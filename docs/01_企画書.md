# 企画書 v1.1 — 位置共有アプリ「Mimamori（みまもり）」

> 家族・友達とリアルタイムで位置を共有し、安全を見守るWebアプリ。
> 日本企業向けポートフォリオ作品。

---

## 1. プロジェクト概要

| 項目 | 内容 |
|---|---|
| **アプリ名** | **Mimamori（みまもり）** ※仮確定 |
| **一言で** | 家族・友達の「今どこ？」がひと目でわかる、プライベートな位置共有アプリ |
| **目的** | 日本企業就職用ポートフォリオ。技術的な見どころ = **リアルタイム通信（WebSocket）** |
| **ターゲット** | 家族（親子）、友達グループ、恋人・同居人 |
| **参考アプリ** | Life360（安全・構造）、Zenly（楽しい見た目）、Find My（シンプルさ） |

### コンセプト
「**見張る**」のではなく「**見守る**」。
監視ツールではなく、**お互いの合意**で位置を共有し、安心を分かち合うアプリ。

### 2.3 F-11 呼び出し（Ping）・応答確認 — 詳細

**目的:** 子どもが電話に出ない・既読にならないとき、親が端末を強制的に鳴らして安否を確認する。

#### フロー
```
[親] メンバー詳細で「呼び出す」をタップ
   │  POST /api/pings  { targetUserId }
   ▼
[サーバー] ping を保存 → WebSocket と Web Push の両方で送信
   │
   ├─(A) アプリを開いている場合 → WebSocket 受信
   │        → 警報音ループ再生 ＋ バイブ ＋ 全画面オーバーレイ
   │          「お母さんが呼んでいます」［大丈夫だよ］ボタン
   │
   └─(B) アプリを閉じている場合 → Web Push → Service Worker
            → 通知表示（requireInteraction）＋ バイブ
              ※音は端末の標準通知音
   ▼
[子] ［大丈夫だよ］をタップ  → PUT /api/pings/{id}/respond { status: OK }
   ▼
[親] 「応答あり ✅」＋ そのときの位置を受信

[子] ［あとで返す］をタップ  → PUT /api/pings/{id}/respond { status: LATER }
   ▼
[親] 「あとで返すと言っています 🕐」（音は止まるが、無応答とは区別する）

⏰ 一定時間（既定3分）どちらも押されない場合
   → 親に「応答なし ⚠️」を通知＋最終位置を表示（エスカレーション）
```

> **なぜ［あとで返す］を用意するか。**
> 逃げ道のない全画面は、授業中・診察中の子どもにとって罠になる。
> 追い詰めればブラウザごと閉じられ、親には**何も届かなくなる**。
> 音を止める道を明示的に用意し、その事実を親へ伝えるほうが情報量が多い。
> 本アプリは 見張る ではなく **見守る**（§1）。
> ※ ガイドライン §5「ボタンは1つだけ」は**主ボタンの数**を指す。
>   ［あとで返す］は目立たないテキストリンクとして置く。

#### 画面
- **送信側（親）:** メンバー詳細（SC-M02）内の「呼び出す」ボタン → 送信後は応答待ち状態を表示
- **受信側（子）:** **SC-M04 呼び出し受信** — 全画面オーバーレイ。大きな文字・大きなボタン1つだけ

#### 実現可能性（正直に評価）

| ケース | 可否 | 内容 |
|---|---|---|
| アプリを開いている（前面・バックグラウンドタブ） | ✅ 実現可能 | WebSocket ＋ Web Audio API で警報音をループ再生。ログイン済み＝ユーザー操作済みなので autoplay 制限に当たらない |
| アプリを閉じている / 画面ロック中 | ⚠️ 一部のみ | Web Push ＋ Service Worker で通知とバイブは可能。ただし**カスタム警報音は鳴らせず、端末の標準通知音になる**（`Notification.sound` は実質未実装） |
| マナーモード / おやすみモードを無視して鳴らす | ❌ 不可能 | ネイティブアプリのみ可能。Web には権限がない |
| iOS / Safari | ⚠️ 条件付き | Web Push は **PWAをホーム画面に追加した場合のみ**動作（iOS 16.4以降）。通常の Safari タブでは受信不可 |

> 📌 **設計方針:** 「アプリを開いている間は確実に鳴る」を主機能とし、
> 閉じている場合は Web Push で「気づかせる」までを保証範囲とする。
> ネイティブアプリと同等の強制力は**Webでは実現できない**と明記する。

### 2.4 技術的制約（正直に明記）

> ⚠️ 本アプリは **Webアプリ（PWA）** のため、ネイティブアプリ（Life360等）と以下の差がある。
> 設計・デモ時はこれを前提とする。

| 制約 | 内容 | 対応 |
|---|---|---|
| **バックグラウンド追跡不可** | ブラウザを閉じる/画面ロックすると位置更新が止まる | アプリを開いている間のみ更新。最終更新時刻を必ず表示（「3分前」） |
| **Battery API 非対応ブラウザあり** | Firefox / Safari は `navigator.getBattery()` を削除済み。Chrome / Edge のみ対応 | 取得できない場合は「不明」と表示。機能の必須要件にしない |
| **GPS精度** | 屋内やWiFi測位では誤差が出る | 精度（accuracy）を保存し、誤差が大きい場合は地図に円で表示 |

### 2.5 F-15 トーク（メッセージ） — 詳細

**位置づけ:** 主役ではない。「今どこ？」と聞くための短いやりとりに絞る。
LINE の置き換えは狙わない（日本の家庭では LINE が既にある）。

**なぜ入れるか:** 位置を見て気になったとき、アプリを離れずに一言送れる。
「迎えに行こうか？」を送るのに別アプリへ移動させると、見守りの流れが切れる。

#### 会話の種類
| 種類 | 相手 | 入口 |
|---|---|---|
| グループトーク | グループ全員 | 地図画面（SC-M01）のトークボタン |
| 個人トーク | メンバー1人 | メンバー詳細（SC-M02）の「メッセージ」 |

#### やること・やらないこと
| 入れる | 入れない（MVP対象外） |
|---|---|
| テキスト送受信、リアルタイム反映 | 画像・動画・ファイル送信 |
| 未読件数 | 既読の個別表示（誰が読んだか） |
| 送信時刻・日付区切り | スタンプ、リアクション、返信引用 |
| 位置を貼って送る（F-15b・余裕があれば） | 通話、グループ通話 |

> ⚠️ **既読表示は入れない。** 「読んだのに返さない」が家庭内の摩擦になる。
> 本アプリの理念は 見張る ではなく **見守る**（§1）。安否は F-11 呼び出しで確認する。

#### リアルタイム配信
位置共有と同じ STOMP 接続を使い回す（接続を増やさない）。
- グループトーク → `/topic/group/{groupId}/message`
- 個人トーク → `/user/queue/message`

送信は REST（`POST /api/conversations/{id}/messages`）で行い、
サーバーが保存してから WebSocket で配信する。**送信経路と配信経路を分ける**ことで、
オフライン時の再送やバリデーションを REST 側に寄せられる。

### 2.6 F-04 SOS の操作方法 — なぜ「長押し」をやめたか（2026-08-04 変更）

**変更前:** 3秒長押しで発信
**変更後:** タップ → 5秒カウントダウン → 自動送信（カウント中はタップ1回で取り消し）

#### 判断の根拠

**① 誤りの重さが左右で違う**

本アプリの SOS は **家族グループにだけ**届く（`sos_alerts.group_id`）。110番・119番へは飛ばさない。

| 誤り | 結果 |
|---|---|
| 誤って送ってしまう | 家族が余分な通知を1件受け取り、電話を1本かける |
| 送れなかった | 助けが必要な人に助けが届かない |

損失がこれだけ非対称なら、設計は**「送れる」側に倒す**べき。
長押しは軽いほうの誤りを防ぐために、重いほうの誤りを増やしていた。

**② 長押しは「端末を持ち続けられること」を前提にしている**

SOS が最も必要な状況は、まさにその前提が崩れる状況である。

- 腕を引かれて端末が手から離れる → 3秒に届かず **何も送られない**
- 手が震えて指がボタンから外れる（`pointerleave`）→ **何も送られない**
- 意識を失って手を放す → **何も送られない**

長押しは「操作できなくなること」を**無信号**に変換してしまう。
本来それ自体が緊急の合図であるべきなのに。

**③ 無反応の3秒は人を不安にさせる**

押している間に手応えがないと「壊れている」と感じて指を放す。
カウントダウンなら残り秒数・振動・リングで進行が見え、放さずに済む。

#### 誤発報への対策（長押しの代わり）

- 地図画面の SOS ボタンは **画面を開くだけ**。そこでは送信しない（2ステップ必要）
- カウント中は大きな取り消しボタンを出す。**1タップで止まる**
- **送信後**の取り消しだけは長押し（1.5秒）にする。本物の通報を誤って消さないため

> 参考: iPhone の緊急SOS、自動車の eCall も同じ「カウントダウン＋取り消し」方式。
> 「押し続けさせる」のではなく「止めさせる」のが緊急系の定石。

## 5. DB設計（概要 / 14テーブル）

```
users            ユーザー
 ├─ group_members ─┬─ groups        グループ（サークル）
 │                 └─ places        登録場所（ジオフェンス）
 ├─ locations      位置履歴（時系列）
 ├─ place_events   到着/出発イベント
 ├─ sos_alerts ────── sos_responders  「向かっています」と答えた人
 ├─ pings          呼び出しと応答
 ├─ notifications  通知
 ├─ conversations ─┬─ conversation_members  参加者と既読位置
 │                 └─ messages              メッセージ本文
 └─ push_subscriptions  Web Push 購読情報
```

| テーブル | 主なカラム |
|---|---|
| `users` | id, email, password_hash, name, avatar_color, created_at |
| `groups` | id, name, type, invite_code, created_by, created_at |
| `group_members` | id, group_id, user_id, role(OWNER/MEMBER), share_location(bool), joined_at |
| `locations` | id, user_id, lat, lng, accuracy, battery_level, recorded_at |
| `places` | id, group_id, name, icon, lat, lng, radius_m, created_by |
| `place_events` | id, place_id, user_id, event_type(ARRIVE/LEAVE), occurred_at |
| `sos_alerts` | id, user_id, group_id, lat, lng, status(ACTIVE/RESOLVED), triggered_at, resolved_at |
| `sos_responders` | id, sos_alert_id, user_id, responded_at ※SC-S02。誰が向かっているか分からないと家族全員が同時に駆けつけてしまう |
| `pings` | id, from_user_id, to_user_id, status(SENT/OK/LATER/NO_RESPONSE), sent_at, responded_at |
| `notifications` | id, user_id, type, payload(JSON), is_read, created_at |
| `conversations` | id, group_id, type(GROUP/DIRECT), created_at ※DIRECT は2人だけの会話 |
| `conversation_members` | id, conversation_id, user_id, last_read_at ※未読件数はこれで数える |
| `messages` | id, conversation_id, sender_id, body, sent_at |
| `push_subscriptions` | id, user_id, endpoint, p256dh, auth, created_at ※Web Push用 |

**ポイント:**
- `locations` は履歴として全件保存 → F-05（位置履歴）に使う。**最新1件が現在地。**
- ジオフェンス判定はサーバー側で行う（位置受信時に `places` と距離計算 → 出入りが変わったら `place_events` + 通知）。
- 位置は **`share_location = true` のグループメンバーにしか配信しない**（F-03 プライバシー）。
- `notifications` は**完成した文章を保存しない**。`type` と `payload`（メンバー名・場所名など）だけ持ち、
  表示する文章は画面側で組み立てる（SC-N01）。理由: サーバーに日本語を埋め込むと、
  文言修正のたびに過去分と食い違う。英語対応も後から効かなくなる。

## 6. リアルタイム設計（見どころ）

### WebSocket トピック（2026-08-17 実装済み）

接続先は `/ws`。**認証は STOMP の CONNECT フレームの `Authorization: Bearer …`**。

> ⚠️ ブラウザの WebSocket API はハンドシェイクに独自ヘッダーを付けられないため、
> HTTP の `JwtAuthFilter` は WebSocket に効かない。`StompAuthInterceptor` が
> CONNECT フレームを見て接続に Principal を結びつける。
> トークンを URL のクエリに付ける手もあるが、アクセスログやプロキシに残るので避けた。

| トピック | 内容 |
|---|---|
| `/topic/group/{groupId}/location` | メンバーの位置更新。⚠️ 共有オフのグループには配らない |
| `/topic/group/{groupId}/sos` | SOS の発信・解除・「向かっています」 |
| `/topic/conversation/{id}/message` | 新着メッセージ（F-15）。グループ／個人とも同じ形 |
| `/user/queue/ping` | **自分宛の呼び出し**と、その応答・無応答（個人宛なので topic ではなく user queue） |

**送信は REST のまま。** WebSocket は「配る」だけに使う。
保存の成否を HTTP のステータスでそのまま返せるほうが、画面のエラー処理が素直になるため。

**当初の案から変えたもの**
- `/topic/group/{id}/message` + `/user/queue/message` の2本立て → `/topic/conversation/{id}/message` の1本。
  会話に id がある以上、グループか個人かで宛先を分ける理由が無い
- `/user/queue/ping-response` を廃止し `/user/queue/ping` に統合。
  同じ「呼び出し」の状態変化なので、受け取る側は status を見れば足りる
- `place-event` と `presence` は未実装。到着/出発は通知（SC-N01）で足りており、
  presence は Web の制約（バックグラウンド追跡ができない）と相性が悪い

### 位置更新の流れ
```
[ブラウザ] watchPosition()
    │  10〜30秒ごと / 一定距離移動時
    ▼
[POST /api/locations]  { lat, lng, accuracy, batteryLevel }
    │
    ▼
[Spring Boot]
    ├─ locations に保存
    ├─ places と距離判定 → 出入りがあれば place_events + notification
    └─ WebSocket でグループへ配信
           │
           ▼
[他メンバーのブラウザ] 地図のピンが動く
```

### 送信頻度の設計
- 通常: **30秒ごと**、または **20m以上移動**したとき
- SOS発動中: **5秒ごと**（正確な追跡が必要なため）
- 共有OFF時: **送信しない**

## 7. API設計（主要エンドポイント）

**レスポンス形式（2026-08-14 確定）**
成功時は JSON をそのまま返す（`{ success, data, message }` のような包みは使わない）。
失敗は HTTP ステータスで表し、本文は `{ "message": "日本語の説明" }` の1形式に統一する。

> ⚠️ 当初は包み形式を書いていたが、包みの中に `success: false` を入れて HTTP 200 を返すと、
> ブラウザにも監視ツールにも「成功」に見えてしまう。ステータスコードで表すほうに変更した。

**認証方式（2026-08-14 確定）**
`Authorization: Bearer <JWT>` ヘッダー。**HttpOnly Cookie は使わない。**

> ⚠️ 当初は Cookie と書いていたが、フロント（Vercel）と API（Railway）が別ドメインになるため、
> クロスサイト Cookie の制約（SameSite=None; Secure、CORS の allowCredentials）が増える。
> Bearer なら CSRF も成立しないため `csrf.disable()` にできる。
> 代償として、トークンは localStorage に置くので XSS に弱い（承知のうえ）。
